# Contributing Setup

This documents the steps to set up a local development environment for Content
Sync Toolkit.

## Required Software

### .NET Runtime

.NET SDK 10.0 or newer

- <https://dotnet.microsoft.com/en-us/download/dotnet/10.0>
- See `global.json` for the specific SDK requirement

### C# Editor

- VS Code/VS
- Cursor
- Rider

### Database

SQL Server 2019 or newer compatible database

- [SQL Server Linux](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-setup?view=sql-server-ver15)

### SQL Editor

- VS Code with the official [MSSQL extension](https://marketplace.visualstudio.com/items?itemName=ms-mssql.mssql)
- MS SQL Server Management Studio

## Sample Project

### Database Setup

Running the sample project requires creating a new Xperience by Kentico database
using the included template.

Change directory in your console to `./examples/DancingGoat` and follow the
instructions in the Xperience documentation on
[creating a new database](https://docs.kentico.com/documentation/developers-and-admins/installation#create-the-project-database).

`examples/DancingGoat/.config/dotnet-tools.json` pins the
`kentico.xperience.dbmanager` tool version. That version must match the
Xperience package version DancingGoat actually runs against (currently
`$(XperienceLatestVersion)` in `Directory.Packages.props`, via `VersionOverride`
in `DancingGoat.csproj`) — a mismatch does not fail cleanly. Too-old schema
against newer code throws `"database version does not match project version"`
at startup; too-new schema against DancingGoat's bundled sample content (which
was generated by whatever `Kentico.Xperience.Templates` version was installed
when the project was scaffolded) can fail partway through seeding with an
opaque `ObjectTypeSerializationException`. If you bump `XperienceLatestVersion`,
also update the `dbmanager` tool version and reinstall the matching
`Kentico.Xperience.Templates` package (`dotnet new install
Kentico.Xperience.Templates@<version>`) before regenerating or reseeding.

### Testing the content sync toolkit against two instances

The toolkit's foundation ([content-inventory-foundation](specs/content-inventory-foundation.md))
only does something interesting across two separate Xperience instances
connected by Xperience's own Content Sync, whose configuration the toolkit
uses. To test it locally without duplicating the sample project, run the
*same* `examples/DancingGoat` build twice as separate processes, entirely
differentiated by environment variables — never by committed configuration,
since these values include connection strings and secrets. Kentico requires
the target on **HTTPS with a certificate the source trusts**, and the same
Xperience version on both.

1. Trust the .NET development certificate once per machine (Windows asks for
   confirmation):

   ```powershell
   dotnet dev-certs https --trust
   ```

2. Start both instances, with Content Sync enabled and the same secret of at
   least 32 characters on each:

   ```powershell
   # Terminal 1 — target
   $env:ASPNETCORE_ENVIRONMENT = "Development"
   $env:ASPNETCORE_URLS = "http://localhost:27310;https://localhost:27311"
   $env:ConnectionStrings__CMSConnectionString = "<target database connection string>"
   $env:ContentSynchronization__Target__Enabled = "true"
   $env:ContentSynchronization__Target__Secret = "<content sync secret, 32+ characters>"
   dotnet run --no-launch-profile

   # Terminal 2 — source
   $env:ASPNETCORE_ENVIRONMENT = "Development"
   $env:ASPNETCORE_URLS = "http://localhost:27300"
   $env:ConnectionStrings__CMSConnectionString = "<source database connection string>"
   $env:ContentSynchronization__Source__Enabled = "true"
   $env:ContentSynchronization__Source__Secret = "<content sync secret, 32+ characters>"
   $env:ContentSynchronization__Source__TargetUrl = "https://localhost:27311"
   dotnet run --no-launch-profile
   ```

   This relies on Program.cs binding `ContentSynchronizationOptions` from the
   `ContentSynchronization` section, so every value comes from configuration
   instead of being hardcoded.

3. Inspect results on the source instance's admin at **Content management →
   Sync status** (`/admin/content-sync-status`). That requires
   `builder.Services.AddContentSyncToolkitAdmin()` in Program.cs and a valid
   license key on each instance.

4. To check a real sync end to end (for example, that syncing a page moves it
   from **Missing on target** to **In sync**), use Xperience's **Sync** actions
   on the source (for example, **Sync this page** on a page). The target
   applies synchronized content through its "Content sync restoration"
   scheduled task, which runs every 30 seconds. Then use **Refresh** on the
   source's **Sync status** page.

`kentico-xperience-dbmanager` writes the connection string it creates directly
into `appsettings.json`. Since both instances share one project, capture each
generated connection string immediately after creating its database and run
`git checkout -- examples/DancingGoat/appsettings.json` before creating the
next one, so nothing sensitive lands in a tracked file.

## Development Workflow

1. Create a new branch with one of the following prefixes
   - `feat/` - for new functionality
   - `refactor/` - for restructuring of existing features
   - `fix/` - for bugfixes

1. Run `dotnet format` against the `XperienceCommunity.ContentSyncToolkit` solution

   > use the `dotnet: format` VS Code task.

1. Commit changes, with a commit message preferably following the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/#summary) convention.

1. Once ready, create a PR on GitHub. The PR will need to have all comments resolved and all tests passing before it will be merged.
   - The PR should have a helpful description of the scope of changes being contributed.
   - Include screenshots or video to reflect UX or UI updates
   - Indicate if new settings need to be applied when the changes are merged - locally or in other environments

1. This repository is stored with `lf` line endings. If you are developing on Windows you can set your Git config to automatically checkout as `crlf` and commit as `lf`.

   ```powershell
   # git config --global core.autocrlf true
   ```
